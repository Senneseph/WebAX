# Access Revocation

## Introduction

Access revocation is a critical security feature that allows users to remove access for devices that should no longer be trusted. This might be necessary when a device is lost, stolen, or potentially compromised. Effective revocation ensures that unauthorized devices cannot access user data, even if they previously had access.

## Revocation Process

The revocation process involves several steps to ensure that the revoked device can no longer access the application or its data:

1. **Initiation**: Owner device initiates revocation
2. **Registry Update**: Device is marked as revoked in registry
3. **Key Rotation**: New encryption keys are generated
4. **Notification**: Other devices are notified of revocation
5. **Synchronization**: Registry and keys are synchronized to all active devices

## Implementation

### Revocation Function

The following function demonstrates how to implement device access revocation:

```javascript
async function revokeDeviceAccess(deviceId) {
  // Check if current device is owner
  const currentDeviceMetadata = await deviceRegistry.getCurrentDeviceMetadata();
  
  if (!currentDeviceMetadata.isOwner) {
    throw new Error('Only the owner device can revoke access');
  }
  
  // Update device status in registry
  const registry = await deviceRegistry.getRegistry();
  const deviceIndex = registry.devices.findIndex(d => d.id === deviceId);
  
  if (deviceIndex < 0) {
    throw new Error('Device not found');
  }
  
  // Check if device is already revoked
  if (registry.devices[deviceIndex].status === 'revoked') {
    return {
      success: true,
      message: 'Device was already revoked',
      revokedDevice: registry.devices[deviceIndex]
    };
  }
  
  // Mark device as revoked
  registry.devices[deviceIndex].status = 'revoked';
  registry.devices[deviceIndex].revokedAt = new Date().toISOString();
  
  // Update registry
  await deviceRegistry.updateRegistry(registry);
  
  // Generate new encryption keys
  const newKeys = await generateNewEncryptionKeys();
  
  // Notify other active devices
  const activeDevices = registry.devices.filter(
    d => d.status === 'active' && d.id !== deviceId
  );
  
  await Promise.all(activeDevices.map(device => 
    notifyDeviceOfRevocation(device, deviceId, newKeys)
  ));
  
  // Log the revocation event
  await logSecurityEvent({
    type: 'device_revoked',
    deviceId,
    revokedBy: currentDeviceMetadata.id,
    timestamp: new Date().toISOString()
  });
  
  return {
    success: true,
    revokedDevice: registry.devices[deviceIndex]
  };
}
```

### Notifying Other Devices

When a device is revoked, all other active devices need to be notified so they can update their local registry and encryption keys:

```javascript
async function notifyDeviceOfRevocation(device, revokedDeviceId, newKeys) {
  try {
    // Establish secure channel with device
    const channel = await establishSecureChannel(device.id);
    
    // Send revocation notification
    await channel.send({
      type: 'revocation',
      revokedDeviceId,
      newKeys,
      timestamp: Date.now()
    });
    
    // Wait for acknowledgment
    const response = await channel.waitForResponse(30000); // 30 second timeout
    
    if (response && response.type === 'revocation_ack') {
      // Device acknowledged the revocation
      return true;
    }
    
    // No acknowledgment received
    return false;
  } catch (error) {
    console.error(`Failed to notify device ${device.id} of revocation:`, error);
    return false;
  } finally {
    // Close channel
    if (channel) {
      channel.close();
    }
  }
}
```

### Key Rotation

After revoking a device, it's important to rotate encryption keys to ensure the revoked device can no longer decrypt new data:

```javascript
async function generateNewEncryptionKeys() {
  // Generate new symmetric encryption key
  const newDataKey = await window.crypto.subtle.generateKey(
    {
      name: 'AES-GCM',
      length: 256
    },
    true,
    ['encrypt', 'decrypt']
  );
  
  // Export the key for distribution
  const newDataKeyBuffer = await window.crypto.subtle.exportKey(
    'raw',
    newDataKey
  );
  
  // Convert to Base64 for storage and transmission
  const newDataKeyBase64 = btoa(
    String.fromCharCode.apply(null, Array.from(new Uint8Array(newDataKeyBuffer)))
  );
  
  // Store the new key
  await secureStorage.set('data_key', newDataKeyBase64);
  
  // Return the key for distribution to other devices
  return {
    dataKey: newDataKeyBase64,
    keyId: generateUUID(),
    createdAt: new Date().toISOString()
  };
}
```

## Handling Revocation Notifications

Devices need to handle revocation notifications when they receive them:

```javascript
async function handleRevocationNotification(message) {
  // Verify the message comes from the owner device
  const registry = await deviceRegistry.getRegistry();
  const ownerDevice = registry.devices.find(d => d.id === registry.ownerDeviceId);
  
  if (!ownerDevice || message.senderId !== ownerDevice.id) {
    throw new Error('Revocation notification must come from owner device');
  }
  
  // Update local registry
  const deviceIndex = registry.devices.findIndex(d => d.id === message.revokedDeviceId);
  
  if (deviceIndex >= 0) {
    registry.devices[deviceIndex].status = 'revoked';
    registry.devices[deviceIndex].revokedAt = new Date(message.timestamp).toISOString();
  }
  
  await deviceRegistry.updateRegistry(registry);
  
  // Update encryption keys
  if (message.newKeys) {
    await secureStorage.set('data_key', message.newKeys.dataKey);
    await secureStorage.set('key_id', message.newKeys.keyId);
    await secureStorage.set('key_created_at', message.newKeys.createdAt);
  }
  
  // Log the event
  await logSecurityEvent({
    type: 'device_revocation_received',
    revokedDeviceId: message.revokedDeviceId,
    timestamp: new Date().toISOString()
  });
  
  // Send acknowledgment
  return {
    type: 'revocation_ack',
    revokedDeviceId: message.revokedDeviceId,
    timestamp: Date.now()
  };
}
```

## Automatic Revocation

In addition to manual revocation, consider implementing automatic revocation based on security policies:

```javascript
async function checkForAutomaticRevocation() {
  const registry = await deviceRegistry.getRegistry();
  const currentDeviceMetadata = await deviceRegistry.getCurrentDeviceMetadata();
  
  // Only the owner device can perform automatic revocation
  if (!currentDeviceMetadata.isOwner) {
    return;
  }
  
  const now = new Date();
  const inactivityThreshold = 90 * 24 * 60 * 60 * 1000; // 90 days in milliseconds
  
  // Find devices that have been inactive for too long
  const inactiveDevices = registry.devices.filter(device => {
    if (device.isOwner || device.status !== 'active') {
      return false; // Skip owner device and non-active devices
    }
    
    const lastActive = new Date(device.lastActive);
    const inactiveDuration = now.getTime() - lastActive.getTime();
    
    return inactiveDuration > inactivityThreshold;
  });
  
  // Revoke access for inactive devices
  for (const device of inactiveDevices) {
    await revokeDeviceAccess(device.id);
    
    // Log automatic revocation
    await logSecurityEvent({
      type: 'automatic_revocation',
      deviceId: device.id,
      reason: 'inactivity',
      inactiveDuration: now.getTime() - new Date(device.lastActive).getTime(),
      timestamp: now.toISOString()
    });
  }
}
```

## User Interface Considerations

The revocation interface should be designed with user experience in mind:

1. **Clear Confirmation**: Require explicit confirmation before revoking access
2. **Explanation**: Explain the consequences of revocation
3. **Status Indication**: Clearly show which devices have been revoked
4. **Undo Option**: Consider providing a time-limited option to undo revocation
5. **Notification**: Inform the user when revocation is complete

## Security Considerations

### Revocation Enforcement

Ensure that revocation is properly enforced:

1. **Key Rotation**: Always rotate encryption keys after revocation
2. **Revocation Lists**: Maintain a list of revoked devices
3. **Authentication Checks**: Verify device status during authentication
4. **Offline Enforcement**: Ensure revocation works even when devices are offline

### Preventing Abuse

Protect against abuse of the revocation mechanism:

1. **Owner Verification**: Only allow the owner device to revoke access
2. **Rate Limiting**: Limit the frequency of revocation operations
3. **Audit Logging**: Log all revocation events for security review
4. **Notification**: Notify all devices when a revocation occurs
